## 1. Что это

Киоск на Raspberry Pi: полноэкранный Chromium с ротацией вкладок, управляющее
HTTP-API, сетевой watchdog и приём AirPlay с iOS. Ставится одной командой
`curl … | bash` на чистую Raspberry Pi OS Lite.

Приложение (`app/main.py`, 1816 строк, FastAPI) — **код Олега**. Оно было
написано до этого проекта и переносимо: ни зашитых IP, ни путей, ни секретов
(IP и ключ Immich передаются query-параметрами). Единственная правка в нём —
автоопределение выхода дисплея, см. грабли §6.3.

Всё остальное в репозитории — обвязка: установщик, systemd-юниты как шаблоны,
скрипты watchdog/восстановления/переключения экранов.

## 3. Архитектура

### Юниты

| Юнит | Что делает |
|---|---|
| `xinit.service` | X + Openbox |
| `surface-api.service` | API Олега на :7000 |
| `net-watchdog.timer` | проверка сети раз в минуту |
| `kiosk-restore.service` | после загрузки возвращает картинку |
| `kiosk-output.timer` | HDMI против встроенной панели, раз в 30с |
| `airplay-video/audio.service` | uxplay и shairport-sync |
| `airplay-watch.timer` | возврат киоска после AirPlay, раз в 20с |
| `kiosk-display-off/on.timer` | расписание гашения (только если задано) |

### Скрипты

Всё в `/usr/local/bin/`, конфиг общий — `/etc/kiosk/kiosk.env`,
лог общий — `/var/log/kiosk.log`, состояние — `/var/lib/kiosk/`.

- `net-watchdog.sh` — лестница: 2 неудачи подряд → передёрнуть Wi-Fi,
  4 → перезапуск NetworkManager, 8 → перезагрузка. Защиты: 150с после
  старта не трогать ничего, перезагрузка не чаще раза в 30 минут. Живость
  меряется **по локальной сети** (шлюз, затем `PROBE_HOSTS`), а не по
  интернету — чтобы падение провайдера не перезагружало киоск.
- `kiosk-restore.sh` — идёт по редиректу `COMBO_URL`, подменяет хост на
  `127.0.0.1` (чтобы пережить смену IP), кеширует цель в
  `/var/lib/kiosk/last-surface.url` — если NAS поднимется позже киоска,
  картинка всё равно вернётся.
- `kiosk-output.sh` — выбирает единственный активный выход.
- `kiosk-display.sh on|off` — гашение панели вместе с подсветкой.
- `airplay-watch.sh` — ловит конец AirPlay-сессии.

### Кто под кем работает

`surface-api`, `airplay-video`, `airplay-audio`, `kiosk-output` — **от
пользователя киоска**, потому что им нужен его PulseAudio и его X-сессия.
`net-watchdog` и `airplay-watch` — от root.

Отсюда следствие: `/var/lib/kiosk` и `/var/log/kiosk.log` должны принадлежать
пользователю киоска, иначе половина скриптов молча падает на записи (см. §6.9).

## 4. Установка

```bash
curl -fsSL https://raw.githubusercontent.com/pelinoleg/pi-kiosk/main/install.sh | bash
```

Неинтерактивный **принципиально**: при `curl | bash` stdin занят скриптом, и
любой `read` съел бы кусок собственного кода. В старом `setup_dashboard.sh`
Олега было четыре таких вопроса.

Идемпотентен, не перетирает существующий `/etc/kiosk/kiosk.env`.
Все настройки — переменными окружения, см. README.

### Раскладка на pi4 — одна папка

Держать отдельно «репозиторий» и «установленное приложение» — это две папки,
которые через месяц никто не помнит. На pi4 они сведены:

```
~/kiosk/          ← git-репозиторий: install.sh, scripts/, systemd/, CLAUDE.md
~/kiosk/app/      ← то, что запускает systemd: main.py, clock.py, .venv
```

Ставится так: `INSTALL_DIR=/home/oleg/kiosk/app bash install.sh` из самого
`~/kiosk`. Установщик замечает, что источник и цель совпали, и пропускает
копирование — иначе `cp` ругнулся бы на одинаковые файлы и `set -e` уронил бы
установку. `.venv`, `__pycache__` и скопированный `start-surface-api.sh`
в `.gitignore`, поэтому `git status` остаётся чистым.

## 5. Как отлаживать

```bash
systemctl status surface-api xinit net-watchdog.timer --no-pager
tail -50 /var/log/kiosk.log
ls -la /etc/systemd/system/          # проверять РАЗМЕРЫ, см. §6.1
cut -d" " -f1 /proc/uptime           # растёт или обнуляется? см. §6.4
cat /var/lib/kiosk/fail_count        # 0 = watchdog не при чём
vcgencmd get_throttled               # 0x0 = с питанием всё хорошо
cat /var/lib/kiosk/active_output
```

Скриншот экрана удалённо — оказался самым полезным инструментом за всю сессию,
позволяет увидеть глазами вместо гадания:

```bash
DISPLAY=:0 XAUTHORITY=/home/<user>/.Xauthority scrot -o /tmp/s.png
```

Со стороны роутера (OpenWrt) — быстрее всего для любых проблем с Wi-Fi:

```sh
logread | grep -i PSK-MISMATCH                 # неверный ключ
logread | grep -i <mac>                        # вся история клиента
logread | grep "disassociated" | grep -oE "STA [0-9a-f:]+" | sort | uniq -c | sort -rn
```

Сравнение числа отвалов между клиентами сразу отвечает, виноват роутер или одно
устройство. `AP-STA-POSSIBLE-PSK-MISMATCH` — неверный пароль;
`excessive missing ACKs` — радиомодуль клиента перестал отвечать, а не «слабый
сигнал».

## 6. Грабли

Всё реально отловленное, с симптомами. Большинство молчаливые — не дают ошибки.

### 6.1. Нулевые файлы после жёсткого зависания → systemd врёт `masked`

Pi повис, ext4 не сбросил данные, все свежезаписанные файлы стали **нулевой
длины**. systemd показывает пустой юнит-файл как `masked` — не как ошибку.
Первая установка пропала целиком и молча.

Установщик после записи проверяет размеры и делает `sync`. **При странностях
смотреть `ls -la /etc/systemd/system/`, а не `systemctl status`.**

### 6.2. `Only console users are allowed to run the X server`

`/etc/X11/Xwrapper.config` из пакета `xserver-xorg-legacy` содержит
`allowed_users=console`, а у systemd-сервиса консольной сессии нет. `startx`
падает, юнит вечно в `activating (auto-restart)`, **Xorg-лог не пишется вообще**.

Нужно `allowed_users=anybody` + `needs_root_rights=yes`. Киоск на 3B работал
только потому, что этот файл когда-то правили руками — ровно тот случай,
ради которого проект и делался.

### 6.3. `HDMI-1` был зашит в `main.py` в восьми местах

На машине с другой панелью (DSI, второй HDMI) всё это промахивается, и молча:
`xrandr` возвращает ненулевой код, поэтому `display-state` рапортует «выключен»
при живом экране, `display-on/off` отдают ошибку, а в ветке mpv команда стоит в
цепочке через `&&` — плеер после неё не запускается вовсе.

Теперь выход определяется один раз при импорте (`_detect_display_output()`),
переопределяется переменной `DISPLAY_OUTPUT`. **Определяется при импорте —
значит после смены выхода `surface-api` надо перезапускать**, это делает
`kiosk-output.sh`.

### 6.4. Аппаратный watchdog перезагружал плату сам

`RuntimeWatchdogSec=20` загнал Pi 4 в цикл: uptime 30–90 секунд, **без паники
ядра и без следов в журнале**. У BCM аппаратный таймер ограничен ~15 секундами.

Вдвойне коварно: на таких сборках `/var/log` часто в tmpfs (log2ram), и сброс
стирает улики собственного сброса.

Теперь по умолчанию **выключен**, включается `HW_WATCHDOG=1`, зажимается до 14с.
Диагностика: uptime не растёт, а `fail_count` софтового watchdog при этом 0.

### 6.5. comitup

Демон провижининга Wi-Fi. Сам управляет NetworkManager и при любой потере связи
сносит подключение и поднимает свою точку доступа. Выглядит как «Pi забыл сеть»
и «не видит SSID» — в режиме AP интерфейс не сканирует эфир. Установщик его
отключает, если находит.

### 6.6. Кабель через Wi-Fi репитер = две подсети

Репитер в режиме роутера выдал `192.168.3.102`, и на Pi стало два интерфейса с
двумя маршрутами по умолчанию. Либо кабель напрямую в роутер, либо только Wi-Fi.

Кабель **напрямую** в роутер уживается с Wi-Fi нормально: одна подсеть, метрики
расставляются сами (eth0 = 100, wlan0 = 600), выдёргивание кабеля переключает
на Wi-Fi автоматически.

### 6.7. `ufw` не находится через `command -v`

Он в `/usr/sbin`, которого нет в `PATH` обычного пользователя. Проверка наличия
firewall проваливалась именно на машинах, где firewall есть. Симптом: API
отвечает на `127.0.0.1` и не отвечает из сети — выглядит как сломанный сервис.

### 6.8. uxplay: порт 7000 и `-nohold`

- Порт по умолчанию у uxplay — **7000**, тот же, что у API. Принудительно 35000.
- **Без `-nohold` uxplay держит первого клиента и отказывает всем остальным.**
  Телефон, отвалившийся некорректно, оставляет установленные соединения
  (висели часами), и устройство перестаёт быть доступным для всех. Симптом:
  «AirPlay не показывает вообще», при этом сервисы активны, порты слушаются и
  avahi публикует.
- `-reset 2` рвёт молчащего клиента за ~6с вместо 15.
- **uxplay буферизует stdout**: под systemd целая сессия может не дать ни одной
  строки в журнал. Запускать через `stdbuf -oL -eL`, иначе диагностировать
  придётся по состоянию сокетов.
- После отключения телефона uxplay **оставляет полноэкранное окно с последним
  кадром** — экран выглядит зависшим. Это чинит `airplay-watch.timer`.

### 6.9. Права на общее состояние

`kiosk-output.sh` работает от пользователя, а `/var/lib/kiosk` и
`/var/log/kiosk.log` принадлежали root → `Permission denied`, **но скрипт
возвращал `exit 0`**. Переключение работало, запись о нём — нет, из-за чего
смена выхода определялась бы как новая каждые 30 секунд.

### 6.10. `python-multipart`

Без него эндпоинты с загрузкой файлов (`tts-play-upload`) падают при импорте.
В старом setup-скрипте его не было.

### 6.11. DSI-панель и HDMI

DSI-панель для системы подключена **всегда**, поэтому воткнутый HDMI даёт два
горящих экрана. `kiosk-output.sh` выбирает один и гасит второй вместе с
подсветкой. На DSI `xrandr --off` сам переводит `bl_power` в `4`
(`FB_BLANK_POWERDOWN`) — проверено, панель реально гаснет, а не чернеет.
Скрипт всё равно дожимает подсветку напрямую, на случай другого драйвера.
Пользователь должен быть в группе `video`.

### 6.12. Не Pi, а NAS: immich-kiosk кладёт сервер

Симптом со стороны экрана: immich-kiosk грузится, показывает часы и логотип, но
вечно висит на спиннере, «нет подключения с immich».

Причина — на NAS. `KIOSK_CACHE: false` + `KIOSK_PREFETCH: true` +
`KIOSK_FETCHED_ASSETS_SIZE: 500` заставляют контейнер опрашивать Immich
непрерывно и **без подключённого браузера** — гасить экран киоска бесполезно.
Дальше лавина: htmx-таймаут страницы 8 секунд, запрос под собственной же
нагрузкой не успевает, браузер шлёт новый, брошенный продолжает выполняться.

Доказано `docker stop immich-kiosk`: load average 11.85 → 3.19, активные
запросы postgres 8 → 0 за 100 секунд. NAS: 4 ядра, 15.7 ГБ.

**Вывод для будущего: прежде чем чинить киоск, проверить сервер, который он
показывает.** Полдня ушло на Pi, а виноват был контейнер на NAS.

### 6.13. Ошибки в собственных инструментах

Дважды диагностика врала из-за инструмента, а не системы:

- На macOS **нет команды `timeout`**. `timeout 8 dns-sd … 2>/dev/null` молча
  возвращал пустоту, и AirPlay трижды выглядел нерабочим при живом сервисе.
  Правильно: запустить в фоне и убить через `sleep N; kill`.
- `pgrep -f runinstall.sh` ловит строку собственной ssh-команды и всегда
  отвечает «процесс жив». Та же грабля выстрелила и **внутри API**: `pgrep -f`
  из `run_command` (shell=True) ловил собственный bash, чей cmdline содержит
  паттерн, — часы всегда числились «запущенными». Лечится скобкой в начале
  регэкспа: `pgrep -f '[/]usr/bin/python3 …'`.

Соответственно: `/tmp` очищается при перезагрузке — логи длинных операций писать
в домашний каталог, иначе после ребута от них ничего не останется.

### 6.14. Рестарт `surface-api` убивал браузер вместе с собой

Chromium запускается **из API**, значит живёт в cgroup `surface-api.service`.
С дефолтным `KillMode=control-group` любой рестарт сервиса — установщик,
`kiosk-output.sh` при смене выхода, падение с авторестартом — молча гасил
браузер: чёрный экран, на нём только мышка, все сервисы `active`. Именно так
выглядел «чёрный экран после AirPlay» — AirPlay был ни при чём, киоск убил
повторный прогон установщика.

Лечится `KillMode=process` в юните: при рестарте умирает только сам API,
а осиротевший браузер дожимает первый же вызов `chrome-tabs` (`killall`).

### 6.15. `pkill -f chrome` в API убивает curl самого restore

Обработчик `chrome-tabs` первым делом делает `pkill -f chrome`. Командная
строка curl-а, который этот эндпоинт вызвал, содержит «chrome-tabs» в URL —
и подпадает под паттерн. Пока restore бежал от root (systemd-юнит), pkill от
пользователя до него не дотягивался и всё работало. Стоило запустить
`kiosk-restore.sh` от того же пользователя, что и API, — его curl погибал на
каждой попытке, restore считал их неудачными и **перезапускал браузер пять раз
подряд** (визуально «киоск постоянно перезапускается»), после чего сдавался с
FAILED при фактически восстановленном экране.

Вывод: всё, что хочет дёрнуть restore, должно делать это через
`sudo systemctl restart --no-block kiosk-restore.service` (юнит работает от
root, параллельные запуски systemd сериализует), а не запускать скрипт напрямую.

### 6.16. Наследие в main.py, найденное при ревизии 2026-08-06

- **Часы были сломаны молча**: эндпоинты запускали `clock_tk.py`, а файл
  называется `clock.py`. Запуск «удавался» — команда уходит в фон через `&`,
  код возврата всегда 0. Плюс PyQt5 не стоял (часам нужен системный python3 и
  apt-пакет `python3-pyqt5`, теперь он в установщике).
- **Ложная тревога про креды вебки**: зашитые в `/surface/webcam` адрес, логин
  и пароль сначала были приняты за утечку и убраны. Олег объяснил: это **не его
  камера** — публичная камера пляжа Бадалоны, владельцы сами опубликовали
  доступ у себя на сайте. Значения возвращены как дефолты параметров, и это
  осознанно. Не «чинить» повторно.
- **Вложенный литерал в f-строке — не f-строка**: температурный JS-блок вебки
  лежал внутри `{'''...''' if show_temp else ''}` — `{{` в нём не
  разэкранировались, и при `show_temp=true` страница получала битый JS,
  который убивал весь `<script>`, включая обновление картинки.

### 6.17. `kiosk-output` сам включал намеренно выключенный экран

Симптом: «выключил экран через `display-off`, через 10–20 секунд он сам
зажёгся». Сторож выходов на каждом тике (раз в 30с) видит подключённую панель
без установленного режима и делает ей `xrandr --auto` — включение погашенных
выходов и есть его работа, ничего не логируется. Расписание ночного гашения
ломалось бы точно так же.

Лечение — флаг `/var/lib/kiosk/display_off`: его ставят `display-off` (API) и
`kiosk-display.sh off`, снимают `display-on`, `kiosk-display.sh on` и любой
эндпоинт, который принудительно включает экран (`chrome-tabs`, `play`,
`webcam`). `kiosk-output.sh` при живом флаге не трогает ничего. Проверено:
панель пережила два тика сторожа тёмной, оба пути (API и скрипт) работают.

Обратная сторона той же монеты: **AirPlay к погашенному экрану** рисовал
зеркало на тёмной панели — `airplay-watch` убирал браузер, но экран не будил.
Теперь при старте сессии он сначала дёргает `display-on` (fallback — снять
флаг и отдать панель сторожу выходов), потом `kill-all`. Матрица стыков
режимов прогнана целиком; сессию AirPlay можно имитировать без телефона:
`sleep 60 | nc 127.0.0.1 35001` — установленное TCP-соединение на порт uxplay
и есть «сессия» для вотчера (не забыть добить nc, он живёт после EOF).

## 7. Что не проверено

- Переключение на HDMI на живом железе — кабель к pi4 на момент написания не
  подключался. Логика отработала вхолостую (`active_output=DSI-1`).
